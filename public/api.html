Developer API

← back to the races

marblerun.fun runs a nonstop, provably-fair marble tournament: 100 marbles, 25 deterministic races, one champion, forever. Everything the viewer knows is available over a free public API — build a prediction game, a stats site, a stream overlay, a Discord bot, whatever rolls your marbles.

Why it's build-on-able

Every race is a pure function of two published integers: a track seed (builds the course) and a race seed (drives the physics). Both are broadcast ~30 seconds before the race runs, and the server, every viewer, and your code can reproduce the exact same finishing order from them — the sim is deterministic and open source (github.com/bryanbrinkman/marblefun). Nobody — including the house — can change an outcome without changing the seeds everyone already saw. That's the whole trust model, and it's verifiable.

The race lifecycle (a.k.a. your betting window)

race_announced T−30s
Seeds, the 5-marble roster, and scheduledStart (epoch ms) go public. Open your prediction window here.
race_start T+0
The gate opens. Close your window — the outcome is now physically unfolding (and was always determined by the seeds).
race_result ≈ T+60–120s
Official finishing order with times, revealed after the marbles visibly cross the line. Settle up. Ranks 1–5; a stuck marble records a timeSec: null DNF.
tournament_complete every ~25 races
A champion is crowned; a fresh 100-marble tournament starts about 30 seconds later, forever.

Timing tip: compare scheduledStart against the serverNow included in every message — never your local clock alone.

Quick start

// What's racing next?
const next = await fetch('https://marblefun.fly.dev/api/next').then(r => r.json());
console.log(next.race.raceKey, next.race.roster, new Date(next.race.scheduledStart));

// Live events
const ws = new WebSocket('wss://marblefun.fly.dev/ws');
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'race_announced') openWindow(msg.race);   // seeds + roster + start time
  if (msg.type === 'race_start')     closeWindow(msg.raceKey);
  if (msg.type === 'race_result')    settle(msg.raceKey, msg.result); // [{rank, marbleId, …}]
};

CORS is open (Access-Control-Allow-Origin: *) on all /api/* endpoints, so this works straight from a browser.

REST endpoints

GET/api/state

The full tournament snapshot — same payload a fresh viewer boots from: all rounds and races (seeds, rosters, results so far), standings for all 100 marbles, the current race phase, the champion if crowned, serverNow and announceLeadMs.

GET/api/next

Just the upcoming (or in-progress) race — the essentials for a prediction window:

Verifying a result yourself

Clone the repo, serve public/, load the game, and replay any race from its seeds — the returned order will match the API's result byte for byte:

// with public/marble_run.html loaded in a same-origin iframe or window
marbleAPI.newCourse(1970251534);          // trackSeed from the API
const sim = marbleAPI.simulateRace(3324241325);  // raceSeed from the API
console.log(sim.results);                 // identical order + times to race_result

This is what the server itself does — it has no other source of truth.

House rules

  • Fair use: prefer the WebSocket over polling; if you must poll, keep it to one /api/state every few seconds. Be gentle — this runs on a small box.
  • No keys, no signup: the read API is open. If your project gets serious traffic, say hi so we don't mistake you for a runaway script.
  • Stability: payload shapes above are intended to stay stable; new fields may appear — ignore what you don't recognize.
  • Legal: if you build real-money anything on top of this, the laws of your jurisdiction are entirely your problem. The marbles accept no liability. 🏁
